# CSA AARM v1.0 × AAR v0.2.0 — component-level compatibility matrix (DRAFT)

Date: 2026-09-26. Status: draft against `v0.2.0`; re-fetch aarm.dev/spec and /conformance before any external use (a v2.0 is announced).
Scope: one question — which AARM requirements does the AAR *record format* carry, which are outside a record format's remit, and where are the gaps. This is not an assessment of any runtime.

## AARM R5 and R6, verbatim (https://aarm.dev/spec, 2026-09-26)

> **R5 Tamper-evident receipts — MUST.** "The system MUST produce a tamper-evident action receipt for every evaluated action. Each receipt must include at minimum: the original action, the decision, the timestamp, and the policy context used in evaluation. Receipts must be verifiable against unauthorized modification."

> **R6 Identity binding — MUST.** "Every action receipt MUST be cryptographically bound to an agent identity. The binding must be verifiable and must uniquely identify the agent that initiated the action, supporting non-repudiation."

AARM's R5 *test* row adds content the R5 text does not: "Generate receipts for ALLOW, DENY, MODIFY, STEP_UP, DEFER → Requester context, delegation chain, and policy version/hash present per schema" (https://aarm.dev/conformance). Those three items are mapped as R5.d sub-rows.

## Matrix

Scope column: **runtime** = an obligation on the intercepting/deciding system; **record** = an obligation on what the receipt carries. AAR is a record format plus an offline verifier; it has no runtime obligations of its own beyond D-66's commit-before-send rule, which binds every AAR-3 enforcement point.

## (a) What AARM requires that AAR does not and will not do

AAR is a record format, an offline verifier, and a set of byte-pinned test vectors (`README:36-37`: "AAR is the wire format, the conformance rules, and a free verifier for that record"). It does not intercept actions (R1), accumulate session context for a policy engine (R2), evaluate policy or intent alignment (R3), produce authorization decisions (R4), track semantic drift (R7), export OpenTelemetry (R8), or scope credentials at execution time (R9). Those are obligations on a runtime — AARM's "control plane … that sits between an agent and the environments it can affect" (Definitions, https://aarm.dev/spec). AAR's own related-work note on Arcade says the same about runtimes generally: "Arcade governs what an agent may do and runs it. AAR specifies what can be proven afterward." (`docs/related-work-addendum-2026-09-26.md:70-71`). The honest framing is that an AARM-shaped control plane is a *candidate producer* of AAR receipts, and AAR is a *candidate receipt schema* for an AARM implementation's R5/R6 — with the MODIFY/DEFER and one-binding-vs-two-key differences above resolved first.

## (b) What AAR records that AARM's text does not require

Quoted absences are from https://aarm.dev/spec and https://aarm.dev/conformance as retrieved 2026-09-26; "not required" means the text is silent, not that a given AARM implementation lacks it.

1. **Graded outcome.** AARM's R5 minimum content is "the original action, the decision, the timestamp, and the policy context used in evaluation"; the Action Receipt definition lists "the action, decision, timestamp, agent identity, and relevant evaluation context." Neither names an outcome. AAR carries `outcome-evidence-level` accepted / dispatched / device_acknowledged / independently_sensed / contradicted / unknown (`cddl:76-82`) and a separate `outcome_observation` node (`cddl:536-542`); `RFP:89-100` Clause 4 bars "verified" without a named independent observer.
2. **Observer in a distinct failure domain.** AARM has no observer concept in R1–R9 or the definitions. AAR requires `independently_sensed` to come from an `outcome_observer` whose `device-identity.failure_domain_id` (`cddl:302`) is distinct, else `evidence/observer-not-independent` (`CONF:545`; KAT `negative/evidence-observer-not-independent.cbor`).
3. **Refusal whose non-execution is checkable from the record.** AARM *does* require "denial receipt generated" (R1 test), so a denial record is not an AAR extra. What AARM's text does not require is that the receipt set itself let a later reader confirm nothing was sent: AAR's record carries `not_dispatched` with a required `refusal_reason` (`CONF:462`), and the RFP pairs that with an "independent transport witness positioned at the dispatch boundary" (`RFP:85-87`). The v0.2 verifier does **not** bar a `dispatch` from naming a refused attempt; that rule is a gap (see `gateway-hook-mapping-v0.1.md` §4) and today the witness log, not the verdict, is what shows nothing was sent. AARM's test observes non-execution at test time.
4. **Reproducible, vendor-free verification.** AARM requires "Verify receipt signature offline → Signature validates" but says nothing about who supplies the verifier or whether verdicts are reproducible. AAR publishes a stdlib-only verifier under Apache-2.0, requires an explicit evaluation time with "No wall-clock fallback" (`CONF:72`), and emits a signed verdict artifact (`CONF:587-600`) that two clean-room implementations reproduce byte-for-byte over 218 fixtures (`README:84`). Caveat from AAR itself: the reference verdict key is a published test key (`README:65-67`).
5. **Epoch-level tamper evidence.** AARM R5 is per-receipt (R2's hash-chain test is SHOULD and conditional: "if hash-chained"). AAR's signed manifest index and RFC 6962 anchor make truncation of a producer-declared epoch detectable (`cddl:858-915`, `965-1003`), while disclaiming ingress completeness (D-72).

## (c) Disclaimer — read before quoting anything above

This is a component-level compatibility assessment of a record format against a runtime-system specification. It is **not** a conformance claim of any kind, and nothing in it should be read as AAR, the AAR reference toolchain, or any AAR producer having been assessed by, submitted to, or recognized by the AARM Technical Working Group. AAR's own verdict vocabulary and `kats/` fixtures are AAR-internal test terms and have no relationship to AARM's assessment. AARM conformance attaches to a *system* and an *organization*; AAR is neither. AAR meets none of AARM's four Organizational Requirements as published at https://aarm.dev/conformance (2026-09-26), quoted:

- Community engagement — "Verify TWG membership or participation in conformance discussions" → "Organization has an active representative in the AARM community." (None claimed anywhere in the AAR repo; not verified externally.)
- Production deployment — "Confirm the system is deployed and serving active customers" → "System is live in production with at least 5 active production customers running for a minimum of 3 months." (AAR: "implemented twice by one operator, run against real cameras, and not yet adopted by anyone else", `README:38-39`; "Nobody outside this repo has run an emitter yet", `README:90`.)
- Security certification — "Request evidence of certification" → "Organization holds at least one recognized security certification (e.g., SOC 2 Type II, ISO 27001, FedRAMP) relevant to the operating environment." (None claimed in the repo.)
- Benchmarking commitment — "Confirm willingness to participate" → "Organization agrees to participate in future AARM benchmarking efforts measuring policy detection and enforcement metrics." (Not applicable to a record format; AAR has no policy detection or enforcement to benchmark.)

Technical gaps that would also block any future claim by an AAR-emitting runtime: MODIFY and DEFER decisions (R4), deferral-resolution receipt fields (R5 test), identity preservation across deferral (R6 test), OpenTelemetry export (R8). The R6 two-key binding nuance (R6.a) should be surfaced, not smoothed over, in any conversation with the TWG.
